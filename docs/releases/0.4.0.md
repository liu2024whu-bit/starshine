# Starshine Geo 0.4.0

Starshine Geo 0.4.0 turns the public core into a reviewable end-to-end small-vector workflow system.
The release extends the explicit operator registry with bounded analysis operations and adds a
one-way assurance chain for understanding, preparing, checking, executing, and recording workflows.
All implementation, examples, tests, and evidence are maintained in the public repository and use
synthetic or redistributable public material.

## Highlights

- CRS-safe clipping, nearest-feature matching, point-in-polygon attribution, and projected geometry
  metrics extend the bounded operator set without hidden reprojection or automatic geometry repair;
- `plan`, `graph`, and `explain` provide deterministic data-free review surfaces for dependencies,
  defaults, provenance, terminal outputs, and declared CRS behavior;
- Workflow Input Contracts derive preparation rules from the canonical planner and immutable operator
  input metadata rather than maintaining a second workflow model;
- actual-input Preflight checks loaded GeoJSON layers for structure, geometry, CRS, field, uniqueness,
  nullability, scalar, and output-collision requirements without executing spatial operators;
- SARIF 2.1.0 conversion maps completed Preflight findings to repository-relative CI locations with
  stable rules, logical workflow context, and structural fingerprints;
- the deterministic public benchmark corpus now contains eight cases covering the complete bounded
  analysis set, with semantic correctness kept separate from environment-specific timing;
- normal CI uses reviewed direct validation-tool constraints, while a separate scheduled workflow
  continues to test the latest dependency versions permitted by project bounds.

## Architecture

The 0.4 workflow-assurance path is intentionally one-way:

`inspect → validate → plan → graph → explain → contract → preflight → SARIF/run → manifest`

- `operator_registry.py` remains the single reviewed source for execution, named inputs, parameters,
  defaults, public schemas, deterministic flags, and preparation contracts;
- `planning.py` owns data-free dependency and provenance analysis;
- graph, explanation, contract, Markdown, Mermaid, and SARIF code remain presentation or adaptation
  layers rather than alternative validators;
- `preflight.py` consumes planner-derived contracts and checks only actual external FeatureCollections;
- `preflight_sarif.py` converts a completed report and does not load data or execute operators;
- optional file formats remain in adapters and CLI handling, while core workflow APIs accept validated
  in-memory FeatureCollections.

## Compatibility and upgrade notes

- Python 3.10, 3.11, and 3.12 remain supported and are tested from both editable source installs and
  clean installations of the exact built wheel;
- Workflow version 1 remains current;
- GeoJSON remains the canonical in-memory data contract;
- the optional GeoPackage adapter remains isolated behind the `geopackage` extra;
- existing 0.3 workflows remain valid when they satisfy the published Workflow v1 schema;
- the package adds new public commands and reports but does not remove or rename existing 0.3 APIs;
- output fields, CRS requirements, ambiguity policies, and deterministic tie behavior remain explicit.

## Security and data boundaries

Workflow JSON cannot name modules, provide Python callables, execute user code, or invoke unregistered
functions. Starshine does not use `eval`, `exec`, or dynamic imports of user-selected code. Distance
operations require declared projected CRS semantics, overlay and attribution inputs require explicit
CRS rules, and no new operation silently repairs geometry or chooses a CRS.

Canonical plans, contracts, Preflight reports, and manifests avoid machine paths and raw feature
values. SARIF file locations are supplied explicitly by the CLI and must remain within a selected
repository root; absolute, parent-traversing, URL-like, missing, and out-of-root paths are rejected.
Uploading SARIF and granting `security-events: write` remain explicit downstream repository choices.

## Reproducibility and release evidence

The release candidate is required to pass:

- the tracked-file public-boundary audit;
- Ruff and the complete test suite on Python 3.10, 3.11, and 3.12;
- the isolated GeoPackage round-trip job;
- deterministic verification and schema checking for all eight benchmark cases;
- package, citation, changelog, README, and release-note consistency checks;
- wheel and source-distribution builds, Twine metadata validation, and archive inspection;
- non-editable installation of the exact built wheel on Python 3.10, 3.11, and 3.12;
- public API and CLI smoke checks for workflow review, contracts, Preflight, SARIF, bounded operators,
  inspection, execution, and manifests.

## Public source boundary

This release contains no private repository module, private database, proprietary dataset, course
archive, textbook or OCR derivative, internal deployment configuration, personal path, credential,
or unpublished research-delivery artifact. All tracked workflows, geometries, expected outputs,
reports, and benchmark cases are synthetic and maintained directly in this repository.

## Known limitations

- Preflight still accepts in-memory FeatureCollections only; GeoPackage input is currently a CLI and
  adapter design task rather than a core API concern;
- Preflight intentionally defers contracts involving produced layers and all execution-time spatial
  outcomes;
- `preflight.py` should be decomposed before another independent check family is added;
- nearest matching and point-in-polygon joining prioritize deterministic reference semantics over
  spatial-index optimization;
- geometry quality reporting is not yet available and Starshine does not automatically repair data;
- the operator registry is a reviewed extension point, not a third-party runtime plugin loader;
- no PostGIS adapter, web interface, or package-index publication is included in this release.
