# Starshine Geo 0.7.0

Starshine Geo 0.7.0 stabilizes the public bounded vector-analysis core around one auditable workflow
path: explicit inputs and CRS assumptions, declarative operator contracts, deterministic review and
Preflight, bounded execution, reproducible outputs, and distribution evidence that can be checked
outside the development checkout.

This release remains an alpha-quality research preview. It is intentionally smaller than a desktop
GIS and does not try to compete on operator count.

## Highlights

- **Geometry assurance without hidden repair.** A read-only geometry-quality API and CLI report
  invalid topology, empty and duplicate geometry, coordinate dimensions and counts, CRS metadata
  state, bounded finding samples, and deterministic report evidence without mutating user data.
- **Explicit GeoPackage workflows.** Preflight and execution can bind named GeoPackage layers
  explicitly, mix GeoJSON and GeoPackage inputs, protect source files from accidental overwrite, and
  persist selected outputs with reproducibility manifests.
- **Deterministic spatial indexing.** STRtree acceleration for nearest-feature and point-in-polygon
  operations is checked against independent exhaustive references so performance work does not change
  public semantics.
- **Bounded overlay expansion.** Deterministic pairwise Intersection and polygon-mask
  Difference/Erase extend the reviewed operator registry while reusing the same Workflow, contract,
  Preflight, execution, and evidence path.
- **Installed-runtime diagnosis.** `starshine doctor` checks package metadata, PROJ, GEOS, the
  declarative registry, and a self-created registry-to-workflow execution without depending on a
  project dataset.
- **Privacy-aware source discovery.** GeoJSON and GeoPackage inventory exposes structural and spatial
  metadata without copying attribute values into reports.
- **Stronger release evidence.** Source and exact-wheel testing spans Python 3.10–3.14, clean
  reproduction runs on Linux, Windows, and macOS, and the public wheel can be handed off in both
  network-assisted and hash-verified offline reproduction bundles.

## Core architecture

The 0.7 line keeps one authoritative dependency direction:

`input adapters → validation → registry → Workflow plan/contracts → Preflight → execution → result + manifest`

The declarative operator registry remains the source of named inputs, parameter rules, defaults,
determinism metadata, output-CRS behavior, and preparation contracts. Planning and report layers
derive from that source rather than maintaining parallel operator or Workflow models.

Preflight is deliberately separate from execution. It checks real supplied inputs against
planner-derived contracts before any spatial operator runs. Runtime execution then uses the same
validated Workflow model and produces a canonical result manifest rather than reconstructing
provenance afterward.

## Reproducibility and release evidence

The 0.7 stabilization work tightened both the artifact and the handoff around it:

- wheels and source distributions are checked against the actual `src/starshine_geo` module tree;
- the reviewed build backend is fixed to Hatchling 1.32.3 and artifacts are validated with Twine;
- source and non-editable exact-wheel checks cover Python 3.10 through 3.14;
- installed reproduction runs on Linux, Windows, and macOS;
- the portable independent-reproduction bundle verifies its scripts, schema, wheel, and manifest
  hashes before creating a fresh virtual environment;
- an optional platform-specific offline bundle additionally hashes every dependency wheel and installs
  with `pip --no-index --find-links`;
- on 2026-09-27, an environment outside Starshine's maintained GitHub Actions execution reproduced
  the exact reviewed 0.7 development-candidate wheel in a fresh Linux x86_64 / CPython 3.13.5
  environment with package-index access disabled.

That independent development-candidate result cleared the external-evidence prerequisite for
preparing this stable candidate. The stable `0.7.0` wheel is still required to pass the repository's
full source, build, installed-wheel, cross-platform, portable-bundle, and offline-bundle checks before
tagging. Detailed independent evidence is retained in GitHub issue #105 and the current procedure is
documented in [REPRODUCING.md](../REPRODUCING.md).

## Compatibility

- Python 3.10, 3.11, 3.12, 3.13, and 3.14 are in the supported public CI matrix.
- Workflow version 1 remains current.
- GeoJSON remains the canonical in-memory FeatureCollection contract.
- GeoPackage support remains optional and isolated behind the `geopackage` extra.
- Runtime versions continue to come from installed package metadata rather than a second hard-coded
  version constant.
- The package remains an alpha-quality research preview; compatibility is reviewed carefully but a
  broad long-term stability guarantee is not yet claimed.

## Deliberate scope boundaries

0.7.0 does not add raster or remote-sensing processing, automatic CRS selection, silent reprojection,
automatic geometry repair, arbitrary Python/plugin execution, PostGIS-scale processing, accounts,
persistence, background jobs, or a browser GIS.

The Server and Web Workbench work tracked for 0.8 remains on a separate stacked draft branch line and
is not included in this release.

## Upgrade notes

Existing Workflow v1 files remain valid when they satisfy the published schemas and operator
contracts. Users adopting the new 0.7 capabilities should pay particular attention to explicit layer
selection, CRS requirements, field-collision rules, and the distinction between data-free planning,
real-input Preflight, and execution.

For a clean installed-wheel verification path, follow
[REPRODUCING.md](../REPRODUCING.md). Distribution preparation and tagging rules are defined in
[RELEASE_PROCESS.md](../RELEASE_PROCESS.md).
